# Fixed-window coverage correction publication

## Why publish

For every fixed physical-support cap, the checked core result constructs a
globally improvable circuit whose complete bounded local search accepts no
improvement. Every proper extracted support is minimum under independent-boundary
semantics. This is a consequential limitation of that search, not a proof of
P versus NP, a rejection of every manuscript route, or a polynomial algorithm.

Publish this finding separately from earned milestones after the exact core merge
passes its release gates. Award no positive row or fixed-checkpoint credit. Keep
the existing earned-row baseline, historical update objects and previous correction
at their original source coordinates. The canonical tracker controls all metrics.

## Source and expectation matrix

| Boundary | Consumers to reconcile before tests | Focused checks |
| --- | --- | --- |
| Thirteen audited conclusions | Reviewed correction contract, update generator and source-bound validator | Missing, renamed, duplicate or changed theorem/module/axiom evidence fails closed |
| Correction-only publication | Current-source binding, update chronology, history fixtures and feed | Successive correction-only releases preserve earlier records; newest batch binds to current source |
| Canonical core merge | Sync source pins, inventory/status/report mirrors, manifest and audit targets | Exact commit/tree and byte identity, not a second Lean build |
| Public explanation | Homepage bottom line, status, FAQ, paper, architecture, README and reviewer/audit documentation | Fixed-cap and independent-boundary scope, unchanged global proof obligations and distinct metrics |
| Current correction summaries | Existing update generator, marked primary pages and current Markdown documents, generator fixture | Exact ledger prose, original notice links, escaped rendering, complete marker set and stale-byte rejection |
| Generated public bytes | Updates, feed, progress surfaces, downloads, report cover, release manifest, release seal, ordered checksum ledger and verifier file descriptors | Generate after source stabilization; reconcile every seal/checksum and fixture/workflow consumer before broad checks |

The reviewed theorem names and their exact types establish the new finding.
The notice also retains the canonical global-stopping non-claim: global no-gain
must be proved, and finite scan failure alone supplies neither that proof nor a
polynomial runtime bound. That general boundary predates this finding and is not
used as a marker that the new correction was already published. Distinct compiled
theorem names require the new notice. The core explanation is
`docs/lean_fixed_window_coverage_obstruction.md`.

Older correction-only snapshots need not appear in earned milestone rows.
They remain publication-history records and must pass the mandatory source audit
against their exact original Git objects, status, progress snapshot and compiled
evidence. Do not rewrite an old notice to the new source or assign it earned credit.

## Release order

1. Prepare the correction adapter, history handling and hostile tests without
   changing the currently published source pin or generated pages.
2. Require the normal core PR checks and clean exact-head verification. Merge
   manually, record the actual merge commit/tree, and pass exact-merge gates.
3. Synchronize from that clean verified merge. Append the separately labelled
   notice with its actual publication timestamp; preserve all prior records.
4. Reconcile the complete active site and expectation chain, then generate and
   seal current bytes. Keep PDF page totals out of reader-facing progress copy.
5. Run focused, source-bound and full site checks, followed by normal site PR
   and exact-merge release gates. Reuse core proof and report evidence.
6. Deploy the exact verified site merge through the authorized interface, verify
   production independently, and verify the repository backups as required.
7. Continue research on global coverage with proved construction and complexity
   bounds; another local example must not substitute for that obligation.

During preparation, keep the previously verified source pin until the exact-core
merge gates pass. Only then synchronize current publication pins. Preparatory
adapter validation is not publication or deployment.

The current-summary adapter stays inactive for the existing unmarked publication.
When the new correction notice is synchronized, every configured current surface
must contain its `CURRENT_CORRECTIONS` marker pair. The existing update generator
then renders the complete reviewed correction list into those regions, including
the homepage bottom line, and rejects missing, duplicate or stale regions. Add
the markers and reconcile the active narrative in that same source-bound sync.
Historical notice objects and earned-milestone text remain separate inputs.
